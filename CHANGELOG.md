# Changelog

Все заметные изменения «Платформы Голос» (https://github.com/gradosphera/blago-vote).

Формат основан на [Keep a Changelog](https://keepachangelog.com/ru/1.1.0/),
проект придерживается [Semantic Versioning](https://semver.org/lang/ru/).

## [1.10.10] - 2026-09-08

### Исправлено

- **Заявки мультикошелька с полем адреса падали с «Invalid address. Got [object Object]».** `Address.parseFriendly` в `@ton/core` 0.60 уже возвращает `AddressInfo` (`{ address, isBounceable, isTestOnly }`), а `validateOrderField` для типа «Address» оборачивал результат ещё раз — `toAddress.address` оказывался обычным объектом, и `storeAddress` бросал «Invalid address. Got [object Object]». Теперь значение возвращается без двойной обёртки; это чинит не только заявку «Произвольная заявка» (создание голосования через мультикошелёк-издателя), но и все остальные типы заявок с адресом («Перевод GRAM», джеттон-операции и т.д.). Проверено node-прогоном полной сериализации `validateOrderField → packOrder → newOrderMessage` на реальном BOC заявки ДАО «Градосфера» (`src/multisig/orderTypes.ts`).

## [1.10.9] - 2026-09-08

### Исправлено

- **Ошибка «Invalid address. Got EQDExlp6…» при создании голосования через мультикошелёк-издателя.** `ProposalDeployer.fromInit` в `ton-vote-contracts-sdk` собран на собственном инстансе `ton-core` (0.48), а в заявку передавался адрес ДАО из `@ton/core` (0.60): `storeAddress` SDK проверяет `instanceof Address` своего `ton-core` и падает с «Invalid address». Теперь адрес создаётся классом `Address` из `ton-core` (он уже является прямой зависимостью приложения). После нажатия «Создать» интерфейс собирает заявку «Произвольная заявка» `FwdMsg` (получатель — деплоер предложений ДАО, `0:662515e05c26e121fd35333b92cb0d4a50c599b4362077a606f8b10496b44c36`, комиссия «0.25» GRAM) и открывает интерфейс мультикошелька; после подтверждения подписантами предложение появляется в ДАО. Проверено node-прогоном `buildCreateProposalOrder` на реальном ДАО «Градосфера»: ячейка `FwdMsg` собирается бит-в-бит как `newProposal` из SDK (opcode `1690551268`, destination `0:662515e0…`, body `1496883659`, флаги body/code/data) (`src/multisig/createProposalOrder.ts`).

- **Подписант мультикошелька-издателя не мог создать предложение («Вы не можете создать предложение»).** `api.ton.vote` для ДАО «Градосфера» отдаёт устаревшие роли (`proposalOwner` продублирован из `owner`, `0:7b7db64f…`, вместо настоящего издателя — мультикошелька `0:1b44b985…`), а фоновая сверка обновляет роль только в течение следующих секунд. `usePublisherMultisigSigner` теперь сам сверяет издателя с цепочкой через `verifyDaoWithChain` (дешёвый get-метод, кэш на 60с) и проверяет подпись на настоящем мультикошельке-издателе; `daoRoles.proposalOwner` используется лишь пока цепочка не ответила (`src/multisig/usePublisherMultisigSigner.ts`, `CreateProposal.tsx`, `DaoMenu.tsx`). Проверено node-прогоном: `checkMultisig` на издателе `EQAbRLmFnI7y…` возвращает подписанта `0:a335feb2…` (оба формата `EQCjNf6y…`/`UQCjNf6y…` — один кошелёк).

## [1.10.8] - 2026-09-07

### Исправлено

- **Страница ДАО не загружалась: показывалось «Предложения не найдены» (или бесконечная загрузка), хотя на главной странице предложения ДАО отображались.** Сверка с цепочкой из `1.10.6` стала блокирующей: на странице ДАО интерфейс сначала читал контракт (`getDao` → `getDaoProposals`), а при недоступном/медленном RPC это затягивалось (повторные попытки ~1 минута и дольше) и запрос к API не успевал или вовсе не отрабатывал — список предложений оставался пустым. Теперь данные ДАО и список предложений всегда берутся из API в первую очередь (страница рендерится сразу), а сверка ролей и метаданных с цепочкой выполняется фоном с таймаутом 15 сек и подставляет актуализированные данные через кэш, не блокируя рендер. Проверено headless-Chrome: страница `/ЕQДехлп6…` отрисовывается за ~8 сек с предложениями, без «Предложения не найдены» (`src/query/getters.ts`).

## [1.10.7] - 2026-09-07

### Добавлено

- **Создание предложений через мультикошелёк-издателя.** Если издателем предложений ДАО (`proposalOwner`) является мультикошелёк, а подключённый кошелёк — подписант (или инициатор) этого мультикошелька, в меню ДАО появляется пункт «Создать предложение». При отправке формы вместо прямого вызова контракта создаётся заявка «Произвольная заявка» в мультикошельке: тело сообщения `FwdMsg` контракту ДАО (получатель — адрес ДАО, сумма — комиссия создания предложения, `0.25` GRAM для «Градосферы»), после подтверждения подписантами транзакция идёт на ДАО и предложение публикуется. Присутствие подписанта определяется через `usePublisherMultisigSigner` (проверка цепочки мультикошелька, порт из gradoshpera-multisig), тело сообщения собирается `buildCreateProposalOrder` бит-в-бит как в `newProposal` из `ton-vote-contracts-sdk` (проверено хешами ячеек для развёрнутого и неразвёрнутого деплоера). Подписант видит свою заявку на странице мультикошелька и подтверждает её обычным образом (`src/multisig/createProposalOrder.ts`, `src/multisig/usePublisherMultisigSigner.ts`, `src/pages/dao/CreateProposal/CreateProposal.tsx`, `src/pages/dao/dao-menu/DaoMenu.tsx`).

## [1.10.6] - 2026-09-07

### Исправлено

- **Изменения ДАО, пришедшие «со стороны» (не через интерфейс в этом браузере), не отображались.** Ранее интерфейс читал роли и метаданные ДАО с индексёра `api.ton.vote`, а сверка с цепочкой срабатывала только при наличии локальной отметки обновления (когда правка сделана через настройки в том же браузере). Если смена издателя/метаданных была подтверждена через мультикошелёк, отметки в браузере не было, и показывались устаревшие данные индексёра (для ДАО «Градосфера» индексёр завис: издатель `EQAbRLm…`, метаданные и ссылки старые). Теперь на страницах, где видны роли и метаданные (страница ДАО, «О ДАО», настройки, страница голосования), интерфейс **постоянно** сверяет с цепочкой роли (`owner`, `proposalOwner`) и указатель метаданных с кэшем на ~60 секунд (`verifyDaoWithChain` в `src/query/hooks.ts`), а при расхождении подставляет данные с цепочки (`syncDaoFromChain`): издатель в карточке «Описание ДАО» и ссылки (Telegram и т.п.) обновляются независимо от индексёра. Лендинг не перегружается RPC — там сверка остаётся только по отметке. (`src/query/getters.ts`, `src/query/hooks.ts`)

## [1.10.5] - 2026-09-07

### Исправлено

- **Смена адреса издателя предложений (и основателя) не отображалась в интерфейсе.** Проверка «актуальности» ДАО после изменений (`compareDaoMetadataWithChain`) сверяла с цепочкой только адрес метаданных; роли (`owner`, `proposalOwner`) интерфейс по-прежнему брал с индексёра `api.ton.vote`, который ещё не отразил смену роли (для ДАО «Градосфера» индексёр завис на старых данных). Теперь сверка расширена (`compareDaoWithChain`): при наличии локальной отметки об обновлении интерфейс проверяет по цепочке и адрес метаданных, и обе роли; при любом расхождении показывает данные прямо с контракта (правду цепочки) и снимает отметку только когда индексёр догонит все три поля. Проверено на реальном ДАО `EQDExlp6…`: на цепочке `proposalOwner = EQAbRLm…` (адрес мультикошелька), индексер отдаёт старый адрес — расхождение определяется, интерфейс покажет новые роли (`src/query/hooks.ts`, `src/query/getters.ts`).

## [1.10.1] - 2026-09-07

### Исправлено

- **Сборка на Vercel падала с TS2322 (`Type 'TonConnect' is not assignable to type 'ITonConnect'`).** Причина: `package.json` указывал `@tonconnect/ui-react@3.0.2`, которой требует `@tonconnect/sdk@4.0.2`, а прямая зависимость была зафиксирована на `4.0.0`; из-за этого при чистой установке образовывались две физические копии `@tonconnect/sdk` (4.0.0 в корне и 4.0.2 внутри `@tonconnect/ui`), у которых типы `TonConnectError` несовместимы. Версия `@tonconnect/ui-react` возвращена на `3.0.0` (совпадает со всеми lock-файлами и установленным окружением, требует `@tonconnect/sdk@4.0.0` — один общий экземпляр).

## [1.10.0] - 2026-09-07

### Исправлено

- **Обновлённые метаданные ДАО (аватар, название и т.п.) не отображались в интерфейсе после обновления через «Настройки».** Причина: фронт по умолчанию рендерит данные с индексёра `api.ton.vote`, а он не отразил смену указателя метаданных ДАО (отдавал старую запись с аватаром, который больше не доступен). Единовременный запас в 90 секунд (чтение с контракта после обновления) не спасал: как только индексёр «догонял» по своему внутреннему времени, интерфейс снова возвращался к его (устаревшим) данным. Теперь после обновления интерфейс сверяет адрес метаданных из индексёра с фактическим указателем на цепочке (`compareDaoMetadataWithChain` в `src/query/hooks.ts`): пока они расходятся, страница ДАО (`src/query/getters.ts`) и списки/сайдбар (`useIsDaosUpToDate`) показывают данные прямо с контракта, а локальная метка снимается только при реальном совпадении адресов — обновлённый логотип не откатывается назад.

## [1.9.0] - 2026-09-04

### Исправлено

- **Окно подключения кошелька не открывалось вовсе** (после клика по кнопке «Кошелек» «ничего не происходило» и локально, и на проде). Причина: TonConnect SDK по умолчанию загружает список кошельков с `https://config.ton.org/wallets-v2.json`, который в ряде сетей недоступен — SDK замирает на инициализации, и модальное окно не рендерится. Создан собственный коннектор (`src/tonConnect.ts`), который подставляет локальную копию реестра кошельков `public/wallets-v2.json` (загружается с того же домена, что и приложение; в `src/main.tsx` в провайдер передан `connector`). `@tonconnect/sdk` добавлен прямой зависимостью.

### Добавлено

- **Выпадающее меню кошелька после авторизации** (`src/layout/Navbar.tsx`). Клик по кнопке «Кошелек» при подключённом кошельке открывает стандартное меню: имя кошелька и полный адрес, пункты «Скопировать адрес» (копирует в буфер обмена с уведомлением «Скопировано») и «Выйти» (отключение от кошелька).

## [1.8.0] - 2026-09-04

### Исправлено

- **Долгая/бесконечная загрузка кнопки кошелька (TonConnect) при открытии страницы.** Причина: манифест TonConnect грузился с мёртвого домена `vote.gradosphera.org`, из-за чего TonConnect не мог завершить инициализацию и кнопка «висела» в состоянии загрузки / не открывала окно подключения. Манифест (адрес в `src/config.ts`) и сам файл `public/tonconnect-manifest.json` (поля `url`/`iconUrl`) переведены на рабочий хост `https://blago-vote.vercel.app`.
- **Кнопка кошелька перерисована на собственную** (`src/layout/Navbar.tsx`). Встроенная `TonConnectButton` показывала свой внутренний спиннер, пока ждала восстановления соединения (`connectionRestored`), и могла «зависнуть» при любых сетевых проблемах TonConnect. Теперь кнопка рендерится мгновенно: без подключения — надпись «Кошелек», при подключении — адрес и имя кошелька; клик открывает стандартное окно TonConnect (`tonConnectUI.openModal()`).

### Добавлено

- **Пагинация «Завершённых голосований» на главной** (`src/pages/daos/ActiveProposals.tsx`). Вместо всех завершённых голосований сразу показываются только 3 последних; кнопка «Далее» (справа, только во вкладке «Завершённые голосования») подгружает следующие 3.

## [1.5.0] - 2026-09-04

### Добавлено

- **Статусы голосований в уведомлениях бота** (`bot/bot.js`). Теперь бот публикует три отдельные вехи для каждого голосования:

## [1.2.0] - 2026-09-02

### Кратко

Telegram-бот теперь устойчиво подключается к Bot API даже в сетях с блокировкой Telegram — через **собственный Cloudflare Worker-релей**, и готов к локальному запуску на Ubuntu.

### Инфраструктура / развёртывание (Telegram-бот)

- **Обход блокировки Telegram через свой Cloudflare Worker-релей** (`bot/cf-api-relay/`)
  - Воркер `worker.js` + конфиг `wrangler.toml`: проксирует `api.telegram.org` на адрес `*.workers.dev`. Сеть Cloudflare доступна там, где заблокирован Telegram (весь диапазон IP Telegram закрыт), а токен бота не попадает третьим лицам — трафик идёт только через собственный воркер.
  - Включается переменной `TELEGRAM_API_BASE` в `bot/.env`; в логе пишется `Telegram API host: <адрес> (релей)`.
  - Воркер изолирует беспорядок HTTP-заголовков Cloudflare: вырезает `content-length`/`content-encoding` и hop-by-hop заголовки, читает тело апстриима целиком (`arrayBuffer`), ставит внутренний таймаут 15 с и отдаёт собственный JSON (`502`) с диагностическими заголовками `x-upstream-status/bytes/error`, если апстриима завис — никаких зависших запросов к клиенту.
  - **Бот-сторона (устойчивость к нестабильной сети):** уменьшен таймаут запроса (60→40 с) и добавлены ретраи (2) с паузой при транзиентных сетевых сбоях. Ключевой фикс: при зависшем теле (заголовки 200 уже пришли, но байты не дошли — симптом DPI на `*.workers.dev`) запрос теперь **всегда** повторяется: раньше частичный ответ принимался за прикладной, и ретрая не было.
- **Локальный запуск на Ubuntu** — раздел «Быстрый старт» в `bot/README.md` и обновлённый `bot/.env.example` (включая инструкцию 0.1 по Cloudflare Worker-релею и проверку `curl`'ом).
- **Диагностика при старте**:
  - `validateConfig()` — проверка конфигурации перед запуском.
  - `checkProxyReachable()` — быстрая проверка доступности SOCKS5-прокси (fail-fast) с понятным выводом (`Proxy OK: …` / `недоступен … гост gost`).
  - Финальная ошибка подключения теперь содержит `BOT_TOKEN`/`proxy`/номер попытки — не «слепое» сообщение.
- **Упрощена конфигурация:** `PROXY` по умолчанию пуст (прямое подключение) вместо жёсткого `socks5h://127.0.0.1:9100`; появилась `TELEGRAM_API_BASE` (по умолчанию `https://api.telegram.org`).
